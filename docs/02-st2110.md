# ST 2110 — what full conformance actually costs

Frame Ferret's scope includes ST 2110-20 (uncompressed video), -30 (PCM audio)
and -40 (ancillary data), as sender and receiver. This document records what
that commits us to, because the gap between "emits packets a receiver decodes"
and "is a conformant sender" is where this subsystem will consume its time.

Nothing in this document has been implemented yet. It is the design constraint
list, written before the code so the code can be judged against it.

## The suite, and which parts bind us

| Standard | What it is | Our position |
|---|---|---|
| ST 2110-10 | System timing; mandates PTP per ST 2059-2 | **Hard requirement.** Everything else rests on it |
| ST 2110-20 | Uncompressed active video over RTP | In scope |
| ST 2110-21 | Sender traffic shaping — profiles N, NL, W | **The hard part.** See below |
| ST 2110-30 | PCM audio, AES67-compatible | In scope |
| ST 2110-31 | AES3 transparent transport | Out of scope |
| ST 2110-40 | SMPTE 291M ancillary data | In scope, as passthrough |
| ST 2059-2 | The SMPTE PTP profile | **Hard requirement** |
| RFC 4566 | SDP, how a stream is described | Required to interoperate |
| AMWA IS-04 / IS-05 | NMOS discovery and connection management | Not strictly required, but expected in any real 2110 plant |

## The bandwidth, stated plainly

ST 2110-20 sends **active picture only** — no blanking — as 10-bit YCbCr 4:2:2,
which is 20 bits per pixel.

| Raster | Active bitrate | With ~5% protocol overhead |
|---|---|---|
| 1080p50 | 2.07 Gb/s | **2.2 Gb/s** |
| 1080p59.94 | 2.49 Gb/s | **2.6 Gb/s** |
| 2160p50 | 8.29 Gb/s | **8.7 Gb/s** |
| 2160p59.94 | 9.95 Gb/s | **10.4 Gb/s** |

`frame-ferret interfaces` prints the 1080p50 and 2160p50 figures next to each
NIC's link speed, because "the 2110 stream is broken" and "the 2110 stream is
on the 1 GbE port" look identical from the operator's side.

Note 2160p59.94 does not fit a 10 GbE link once you account for the 2110-21
leaky-bucket margin. That is not our limitation; it is why 25 GbE exists in
UHD plants.

## ST 2110-21 is the requirement that decides how good we can be

2110-21 defines how evenly a sender must space its packets. It gives three
sender profiles:

- **Narrow (N)** — the tightest. Essentially requires the packet schedule be
  driven by hardware.
- **Narrow Linear (NL)** — slightly relaxed, still very tight.
- **Wide (W)** — tolerant of software-scheduled bursts.

A general-purpose NIC driven by a userspace process on a general-purpose OS
realistically qualifies as **wide**, and only with care: no `sendmmsg` burst
larger than the shaper allows, a busy-wait or high-resolution timer rather than
`nanosleep`, and a core that nothing else is scheduled on.

**This is the honest headline: Frame Ferret will be a wide-profile sender.**
Wide is a legitimate, in-spec profile and many receivers accept it. But some
plant equipment — particularly hardware receivers with small input buffers —
is provisioned for narrow senders and will drop or judder on a wide one. Any
deployment has to be tested against the actual receiver, not against a
software analyser.

Getting to narrow needs one of:

- a NIC with hardware transmit pacing (Mellanox/NVIDIA ConnectX-5 and later
  expose this; Intel E810 has Tx time-based scheduling),
- `SO_TXTIME` with the ETF qdisc on Linux, which needs a NIC and driver that
  support launch-time control, or
- an FPGA/SmartNIC doing the packetisation, which is what broadcast gateway
  products actually do.

None of those exist on macOS.

## PTP is the part that blocks macOS hardest

ST 2110-10 requires the media clock be derived from a PTP-disciplined TAI
timeline, not from the system clock. `rtpTimestamp90k()` in `core/rational.h`
already takes a `taiNs` argument for this reason, and `VideoFrame::ptpLocked`
exists so a free-running timestamp can never be mistaken for a media clock.

The problem is where `taiNs` comes from.

- **Linux** — `linuxptp` (`ptp4l` + `phc2sys`) with `SO_TIMESTAMPING` gives
  hardware timestamps on a supporting NIC. This is the only combination in
  which a software 2110 sender is properly disciplined.
- **Windows** — Windows Server 2019+ has a PTP client; hardware timestamping
  depends entirely on the NIC driver. Workable, less well-trodden.
- **macOS** — there is **no supported hardware timestamping path.** No
  `SO_TIMESTAMPING`, no PTP hardware clock exposed to userspace. A macOS PTP
  implementation is software-timestamped, which typically lands within tens of
  microseconds of the grandmaster under light load and degrades badly under
  load.

Tens of microseconds is fine for **2110-30 audio** and **2110-40 ancillary**.
It is not fine for narrow-profile **2110-20 video**, and it is marginal even
for wide.

### What this means for the plan

Since this is a macOS-first fleet, the sequencing has to be:

1. **2110-30 and 2110-40 first, on macOS.** Both are low-bitrate, both tolerate
   a software-timestamped clock, and both are genuinely useful — a Mac that can
   put 64 channels of AES67/2110-30 audio on the network is a real product on
   its own. AES67 interop also gets us Dante-adjacent testing, which the fleet
   already has capture evidence for.
2. **2110-20 receive, on macOS.** Receiving is far more forgiving than sending:
   no pacing obligation, and the media clock comes off the wire. A Mac that
   *receives* 2110-20 and presents it as a UVC camera is arguably the single
   most useful thing in this whole application.
3. **2110-20 send** — implement on macOS as wide-profile with a software clock,
   label it as such in the UI and the SDP, and treat Linux with a
   hardware-timestamping NIC as the only configuration we will describe as
   conformant.

Step 3 shipping as "wide, software-clocked" is a real constraint to write on
the box, not a defect to hide.

## Things that will be got wrong if not written down

- **2110-20 carries no blanking.** Every raster is active picture only. Code
  that assumes an SDI-shaped frame with VANC/HANC will compute the wrong
  packet count.
- **The pgroup is 5 bytes for 2 pixels**, big-endian, and does not align to a
  byte boundary per component. `PixelFormat::ycbcr422_10_pgroup` exists
  precisely so this never gets confused with v210, which is a *different*
  10-bit packing (6 pixels / 16 bytes, little-endian) that looks superficially
  similar. Confusing the two produces a picture with correct geometry and
  wrong colour — the kind of bug that survives a long time.
- **RTP timestamps wrap at 2^32** — about every 13 hours at 90 kHz. Guarded by
  a test in `tests/test_rational.cpp`.
- **The marker bit** ends a frame, and getting it wrong makes receivers hold a
  frame until the next one arrives, which presents as exactly one frame of
  extra latency and nothing else.
- **2110-30 packet time is not free choice.** 1 ms is the common default; 125 µs
  is what low-latency plants use. AES67 mandates support for 1 ms. Offering
  arbitrary values will produce streams nothing accepts.
- **SDP is the interop contract, not a formality.** Most 2110 receivers are
  configured by pasting an SDP. Ours has to be exactly right — wrong `a=fmtp`
  parameters mean a receiver that connects and shows nothing.
- **Multicast needs the egress interface set explicitly** (`IP_MULTICAST_IF`),
  and the join needs the interface index (`ip_mreqn.imr_ifindex`), not the
  address. `net/interfaces.cpp` already carries `index` for this reason; two
  interfaces can hold the same address after a DHCP reshuffle.
- **IGMP snooping means a receiver that never joins sees nothing**, and a
  sender on a switch without an IGMP querier may find its traffic flooded to
  every port — which is how a 2.2 Gb/s stream takes down an unrelated part of
  a network.
